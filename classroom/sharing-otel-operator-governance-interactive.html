OpenTelemetry Operator · 治理機制

從 CR 到叢集：宣告如何變成事實

給熟悉 Kubernetes Operator Pattern 的架構師：不講 CRD / Reconcile / Webhook 是什麼，直接進設計取捨與七個可以動手操作的機制。 出發點只有兩句話：接入成本壓到幾行 annotation，覆蓋率才可能趨近 100%； 政策收斂到 CR，由控制迴圈強制，而不是靠人記得改設定。

問題一 · 擴散

接不上

靠人手動接 SDK，覆蓋率永遠殘缺；agent 版本升級變成五十個 repo 五十個 PR。

問題二 · 治理

管不動

Collector 設定散落在各服務的 Helm values 裡，想全公司調一次 sampling，等於動所有人的部署。

四個 CR 三個設計決策 spec.mode port 推導 注入語意 env 合併 llm-guard-api 解剖 存量矩陣 endpoint 陷阱 紅線 拓撲分析 trace routing Helm 所有權 版本治理 CR 粒度 失效模式 落地路徑

開場 · 治理單元

四個 CR：各自治理什麼，設計性質怎麼影響用法

先講白話版，四句話對應四個 CR，後面的卡片再展開細節：

OpenTelemetryCollector
規範一台 OTel Collector 要怎麼被部署、部署成什麼 mode（deployment/daemonset/statefulset/sidecar）。
Instrumentation
OTel SDK 的設定範本，決定各語言的 auto-instrument 要怎麼注入、注入什麼參數——它自己不部署任何東西。
OpAMPBridge
讓遠端控制面能治理、管理叢集裡這些 Collector——下指令改設定、觸發滾動更新，都透過它中繼。
TargetAllocator
把 Prometheus 的 scrape target 分配給多個 Collector 副本，讓多副本收 metrics 時不會重複抓。

OpenTelemetryCollector v1beta1 · 唯一 stable

管線拓撲與資料政策

Sampling、遮罩、路由、資源上限。spec.mode 驅動資源組合；spec.config 透傳（決策三）。

對應資產

中央 collector 的目的地；各服務手掛的 sidecar。

Instrumentation v1alpha1

接入標準

Agent 版本、endpoint、propagator、sampler。純範本，不建立任何資源；env 逐項合併——這個性質是 RBAC 設計的支點：可以放平台 namespace、業務團隊唯讀，Pod 用跨 namespace annotation 引用。

對應資產

取代各服務 values 裡那串 OTEL_* env。

OpAMPBridge v1alpha1

Collector 群的遠端控制面

Server 下推的不是 collector config，而是 CR 變更——bridge 改寫 CR、operator 照常 reconcile。控制面疊在 operator 之上，不是繞過它，componentsAllowed 白名單、Git diff 這些既有防線仍然有效。

對應資產

多環境（l- / s- / p-）的控制面選項。

TargetAllocator v1alpha1 · 可獨立或內嵌

Prometheus scrape target 分配

四個裡治理色彩最淡，價值在遷移路徑：prometheusCR.enabled 直接認得現有 ServiceMonitor / PodMonitor，收編不需要重寫任何一份。

對應資產

現有的 serviceMonitors 資產。

開場 · 不讀 code 不會知道的三件事

三個對治理有直接後果的設計決策

跳過 operator 101，只講三個決定「一個政策下推之後會發生什麼」的設計。

機制一 · 收斂速度

決策一：兩個執行點，兩種政策生效語意

Operator 直接擁有的 workload（gateway/agent）走 reconcile 迴圈，持續運作；改 CR 立刻觸發 rolling update，手改被改回。 Webhook 注入的東西（sidecar/instrumentation）只在 Pod CREATE 那一刻生效一次（沒有 UPDATE）； 改 CR 之後，已經在跑的 Pod 與 CR 脫鉤——config 已經烤進去，要等該服務自己下一次部署才追得上。 治理後果：下推一個政策，兩類目標的收斂時間完全不同，平台需要量測「多少 % 已拿到新政策」，不能假設 apply 完就全部生效。

互動實驗

同一次 CR 變更，四個目標各自多久才追上

Gateway 走 reconcile 迴圈；三個服務都掛了 sidecar 注入，只在各自下一次部署（新 Pod CREATE）時才會拿到新設定。

距離改這份 CR，已經過了

四個目標的收斂狀態

gateway-collector（operator 直接管理）
checkout-api（sidecar 注入，約每 2 天部署一次）
notification-worker（sidecar 注入，約每 9 天部署一次）
legacy-billing（sidecar 注入，近 60 天沒有部署）
Mutating webhook 只註冊在 Pod 的 CREATE 事件——沒有任何迴圈會主動幫已存在的 Pod 補推新設定。 像 legacy-billing 這種很少重新部署的服務，會在「政策已下推」和「Pod 實際拿到新政策」之間留下一個沒有上限的落差期。 internal/webhook/podmutation/webhookhandler.go

決策二：failurePolicy=ignore——注入是 best-effort

Operator webhook 不可用時，Pod 照建、只是安靜地沒被注入。設計上合理（observability 元件不該擋業務部署）， 但意味著覆蓋率是要量測的，不是假設的——需要常態盤點「有 annotation 但沒有 initContainer 的 Pod」。 這個取捨不是宿命：operator chart 的 admissionWebhooks.pods.failurePolicy 可以翻轉成 Fail， 親手操作它對 Pod 建立的影響見下方機制五的實驗。

決策三：spec.config 是透傳設計

CR 的 spec.config 就是 collector 設定本體；operator 解析它來推導 Service port、必要的 RBAC，但不改寫語意。 這是遷移成本低的機制根源——現有 Helm chart values 裡的 collector config 可以幾乎原封不動搬進 CR。 同時 spec.image 接受任意 image reference，自建 image、GOMEMLIMIT 這類 runtime env 照掛。

最小 CR
apiVersion: opentelemetry.io/v1beta1 kind: OpenTelemetryCollector metadata: name: gateway spec: mode: statefulset replicas: 2 image: ghcr.io/104corp/otel-collector/collector-contrib:0.142.0 # 自建 image 照用 config: # ← 原汁原味的 collector config，從 Helm values 直接搬 receivers: { otlp: { protocols: { grpc: {}, http: {} } } } exporters: { debug: {} } service: pipelines: traces: { receivers: [otlp], exporters: [debug] }

機制二 · 執行點

spec.mode 決定 operator 長出什麼

同一份 OpenTelemetryCollector CR，換一個 mode 字串，operator 在 reconcile 迴圈裡組出來的資源組合完全不同。 sidecar mode 的特殊性：它讓同一個 Kind 同時活在兩種執行點（決策一）——前三種 mode 走 reconcile，sidecar mode 走 webhook。

機制三 · 透傳設計的延伸

Pipeline 接了什麼 receiver，Service 就開什麼 port

Operator 不替 config 內容建型別，只掃 service.pipelines 裡實際接線的 receiver， 照內建的 port mapping 表把 Service port 湊出來。拿掉一個 receiver，下一輪 reconcile 那個 port 就消失—— 不是「不用宣告 port」，是「宣告 pipeline 就等於宣告 port」。

互動實驗

勾選 receiver，看 Service port 即時重算

Port 號碼取自 operator 內建的 internal/components/receivers/helpers.go mapping 表，非示意數字。

第一部：擴散 · 注入機制

兩個決定接入成本的語意

機制本身很簡單：webhook 讀 annotation → 找 Instrumentation CR → 各語言注入器逐一處理。值得展開的是兩個語意。

service.name 的推導鏈

annotation resource.opentelemetry.io/service.name ＞ Pod label app.kubernetes.io/name ＞ 上層 workload 名稱 ＞ Pod / container 名。意味著大部分服務連 service.name 都不用設—— Deployment 名就是服務名，推導結果與手動設的值相同。

業務團隊寫的全部東西
spec: template: metadata: annotations: sidecar.opentelemetry.io/inject: "opentelemetry/company-sidecar" instrumentation.opentelemetry.io/inject-python: "opentelemetry/company-sidecar"
Pod 建立後 webhook 產出的結果（kubectl describe pod 節錄）
Init Containers: opentelemetry-auto-instrumentation-python ← agent 複製進共用 volume otc-container ← sidecar collector Containers: llm-guard-api: Environment: PYTHONPATH: /otel-auto-instrumentation-python/... OTEL_SERVICE_NAME: llm-guard-api ← 自 Deployment 名推導，沒人手寫 OTEL_RESOURCE_ATTRIBUTES: k8s.namespace.name=...,k8s.deployment.name=...

機制四 · 擴散的縫

Env 是四層優先權，不是覆蓋

由上而下依序檢查，最上層已經設定的值獲勝，下層同名變數會被忽略、不會覆蓋—— 這是「例外留在 app 端，不腐蝕共用範本」的機制根源，也是後面所有「漸進遷移」與「per-service 例外」論證的基礎。

互動實驗

勾選代表「這一層有設定這個變數」，取消勾選代表這一層沒有動它。

依優先權由高到低
① container 原生 env
② 語言區段 env（python）
③ 共用 env（spec.env）
④ CR 欄位推導值

最終寫進 Pod 的值

第一部：擴散 · 場景解剖

llm-guard-api 的 150 行去哪了

values.yaml 從 150 行 OTel 設定變成 3 行 podAnnotations + 1 行刻意留下的例外。重點不是行數， 是每一類設定的去向都對應一條治理原則。

原本的東西去向為什麼
手掛 collector sidecar + 整份 config sidecar 模式的 CR，config 原封不動 決策三的透傳設計。k8s ≥ 1.29 operator 自動以 native sidecar 注入，啟動/終止順序語意不變
OTEL_PYTHON_EXCLUDED_URLS（健檢路徑） 留在 app 自己的 env，不進 CR Per-service 差異不該進共用範本；append-if-not-set 讓 container 自己的值天生贏，不用為此 clone CR
OTEL_SERVICE_NAME 刪掉，自動推導 見上方推導鏈
手工拼的 OTEL_RESOURCE_ATTRIBUTES + 整組 Downward API env 刪掉，由 sidecar 自動蓋章 架構性的一條：手工拼這串的存在，本身就是拓撲缺陷的症狀（見下方拓撲分析）
OTEL_ZERO_CODE_MODE（base image 包裝旗標） 必須拿掉 跟 inject-python 是兩套互斥的 auto-instrument 機制，同時開＝雙重插樁

「after」的 values.yaml 全貌，就這幾行：

web: podAnnotations: sidecar.opentelemetry.io/inject: "llm-guard-api-sidecar" instrumentation.opentelemetry.io/inject-python: "llm-guard-api-instrumentation" instrumentation.opentelemetry.io/container-names: "llm-guard-api" env: - name: OTEL_PYTHON_EXCLUDED_URLS # 唯一刻意留下的例外：per-service 健檢路徑， value: "/healthz,/readyz,/metrics" # 靠 append-if-not-set 天生贏過 CR

這三個 annotation key 各自在決定什麼，以及填的值為什麼是這樣（不是唯一寫法）：

Annotationllm-guard-api 填的值值的意思
sidecar.opentelemetry.io/inject "llm-guard-api-sidecar" 沒有 /，所以是「去 Pod 自己的 namespace 找一個叫這個名字的 OpenTelemetryCollector CR（mode: sidecar）」——llm-guard-api 用的是自己專屬的一份 CR，不是全公司共用的那份
instrumentation.opentelemetry.io/inject-python "llm-guard-api-instrumentation" 同樣沒有 /——去 Pod 自己的 namespace 找一個叫這個名字的 Instrumentation CR，並且指定用 Python 語言的注入器
instrumentation.opentelemetry.io/container-names "llm-guard-api" 逗號分隔的容器名清單，指定 Python agent 要注入進 Pod 裡的哪個 container。這個 Pod 同時掛了 sidecar（見上一行），container 不只一個——不寫這個欄位時 operator 預設只注入 Pod 裡第一個 container，寫死名字才不會因為 container 順序而注入錯地方

三個 key 的值都還有其他寫法,對照 §1.4 組合技那節用過的共用範本模式：

  • "true"——不指名，讓 operator 自動去 Pod 的 namespace 裡找「唯一一份」對應的 CR；namespace 裡有 0 份或超過 1 份都會出錯，所以只適合「每個 namespace 剛好一份 CR」的簡單場景。
  • "<namespace>/<name>"（有 /）——跨 namespace 指到平台共用的那份 CR，例如前面 §1.4 用的 "opentelemetry/company-sidecar"。多數服務會用這種寫法接共用範本。
  • "<name>"（沒有 /，llm-guard-api 用的就是這種）——只在 Pod 自己的 namespace 裡找。llm-guard-api 這裡刻意不用共用範本，是因為它有專屬的 sidecar config，見上面「原本的東西」那張表。
  • container-names 什麼時候非填不可：Pod 有多個 container（掛了 sidecar 之後至少兩個），或是同一個 Pod 同時啟用多種語言注入時——這兩種情況下 operator 會直接擋掉 apply，逼你把 container 名字寫清楚。

提煉：「翻譯」過程不做架構升級，一次只變一個變數；但翻譯過程會暴露既有架構的症狀——手工拼 k8s 屬性那條，下面拓撲分析會處理。

第一部：擴散 · 存量矩陣

全公司服務怎麼收斂成一套模型

存量不會整齊。統一模型：sidecar annotation 人人加，差別只在 Instrumentation 端用哪種 inject annotation。

服務類型Instrumentation annotation團隊要做的事
無 OTel（Java/Python/Node）inject-<lang>加兩行 annotation
已手動裝 javaagent（Dockerfile 塞的）改用 inject-<lang>從 image 移除 agent
已手動裝 SDK（程式內建 provider）inject-sdk（只注入 env、不裝 agent）移除硬編的 provider 配置，改 env 驅動
PHPinject-sdkimage 裝 PECL extension，設 OTEL_PHP_AUTOLOAD_ENABLED

邊界條件：

  • PHP 沒有自動注入（InstrumentationSpec 無 php 欄位）。inject-sdk 是正解：agent 安裝留在 image，endpoint/sampler/resource/propagator 仍由平台 CR 集中下發——治理面不缺角，只缺零改 code。
  • Go 是 eBPF sidecar，要 privileged + otel-go-auto-target-exe，feature gate 預設關。安全審查成本高，建議直接走 inject-sdk + 手動 SDK。
  • 排查「沒被注入」：feature gate 沒開時 webhook 發 InstrumentationRequestRejected Warning event，Pod 照建——又一個安靜失敗點，跟決策二同一族。

Zero-code（免改程式碼）支援的語言，完整清單就這些：

Annotation是否 zero-code機制
inject-java是javaagent jar，掛進 JAVA_TOOL_OPTIONS
inject-nodejs是NODE_OPTIONS=--require ...
inject-python是opentelemetry-instrument 包裝進 entrypoint
inject-dotnet是startup hook / profiler
inject-go算是——但要另外填 OTEL_GO_AUTO_TARGET_EXE，且 sidecar 要 privilegedeBPF uprobe，feature gate 預設關
inject-apache-httpd是（web server 模組，非語言）otel-webserver-module
inject-nginx是（web server 模組，非語言）otel-webserver-module
inject-sdk否——agent 要自己裝好，這個 annotation 只補 env只注入 endpoint/sampler/propagator/resource 等設定值
（PHP 無對應欄位）否——InstrumentationSpec 沒有 php 這個 struct只能走 inject-sdk，agent 自己在 image 裝 PECL extension

Instrumentation CR 大致長怎樣——直接用 lab 裡實際跑得動的那份，比自己編的教學範例更準：

apiVersion: opentelemetry.io/v1alpha1 kind: Instrumentation metadata: name: lab-instrumentation namespace: otel-lab spec: exporter: endpoint: http://localhost:4318 # 明寫，效果等同留空——見下方說明 env: - name: OTEL_EXPORTER_OTLP_PROTOCOL value: http/protobuf - name: OTEL_TRACES_EXPORTER value: otlp - name: OTEL_METRICS_EXPORTER value: otlp - name: OTEL_LOGS_EXPORTER value: otlp - name: OTEL_METRIC_EXPORT_INTERVAL # lab 用途，調快匯出間隔方便馬上看到 metrics value: "5000" propagators: - tracecontext - baggage sampler: type: parentbased_always_on # SDK 端全收，取樣決策交給 gateway 的 tail_sampling java: # 語言區段，7 種語言都是同樣的巢狀結構 env: - name: OTEL_INSTRUMENTATION_COMMON_DEFAULT_ENABLED value: "true" python: env: - name: OTEL_PYTHON_LOG_CORRELATION value: "true" - name: OTEL_PYTHON_LOGGING_AUTO_INSTRUMENTATION_ENABLED value: "true"

classroom/lab/manifests/20-instrumentation.yaml

兩個地方跟前面討論的機制對得上，但寫法不一樣，值得澄清：

1. 這裡完全沒有出現 image／resources。 java/python 區段只有 env——多數團隊實際會寫的就是這樣：讓 operator 決定用哪個 agent image、給多少資源， 自己只管 SDK 行為要開什麼。這兩個欄位要填，通常是遇到平台要自己 pin agent 版本、或 init container 資源配額被 LimitRange 卡住才會用到—— 它們的本質是在描述一個真正會建出來的 container：Java/Python/NodeJS/DotNet/ApacheHttpd/Nginx 都走 init container 模式，查了 internal/instrumentation/python.go，實際建出的 init container 指令就是 cp -r /autoinstrumentation/. /otel-auto-instrumentation-python，把 agent 檔案複製進共用 volume 就結束， app container 再掛載那個 volume用；image 是那個「裝了 agent 檔案」的來源 image，resources 是這個複製動作要吃多少 CPU/記憶體——跟 app 自己的資源配額是兩件事。只有 Go 例外： internal/instrumentation/golang.go 建的是常駐 sidecar（ShareProcessNamespace: true、 privileged），因為 eBPF 需要持續掛著 uprobe，不能複製完就結束——Go 的 resources 才是「agent 常駐要吃多少資源」的字面意思。

2. exporter.endpoint 明寫成 http://localhost:4318，不是留空。 效果跟留空完全一樣——機制六驗過留空時 SDK 也是落回這個值。明寫純粹是讓讀 CR 的人一眼看到「這是要送去同 Pod sidecar」， 不用先知道 SDK 的隱含預設值才看得懂；犧牲一點 verbose 換可讀性，兩種寫法一樣正確。

3. sampler.type 用 parentbased_always_on，不是機率取樣。 註解寫得很清楚：「SDK 端先全收，真正的取樣決策交給 gateway 的 tail_sampling」——呼應拓撲分析那節的架構， 取樣決策留給有完整 trace 視野的 gateway 做，SDK 層不擅自丟資料。

真正的 SDK/API 設定在頂層 spec.exporter/spec.sampler/spec.propagators/spec.resource， 跨語言統一透過 env 灌給 app；語言區段的 env 只是第二層優先權，補該語言專屬的 SDK env。

4. 沒填 image，版本到底是誰決定的？

一句話：就是這個 operator release 打包當下，versions.txt 裡釘死的那個版本 （現在的 repo 是 python 0.63b1、java 2.28.1）——不是動態抓最新版，operator 沒升級，這組版本就不會變。 想知道實際套用的是哪版，直接 kubectl get instrumentation <CR 名字> -o yaml 看 spec.python.image， 比查程式碼準。

底下是這個值怎麼被寫進去的機制，想確認來源再看： 不是等 Pod 建立時才動態查——是 CR 本身有一個獨立的 mutating webhook （internal/webhook/instrumentation_webhook.go 的 Default()），在你 kubectl apply 這份 CR 的當下就把空欄位填死：r.Spec.Python.Image = w.cfg.AutoInstrumentationPythonImage。 所以你 kubectl get instrumentation lab-instrumentation -o yaml 會看到一個具體版本號， 即使你的 git 裡那份 YAML 完全沒寫——etcd 存的 CR 跟你手上的原始檔案不是同一份，apply 那一刻就被寫死了。 連 resources（未填時 500m/256Mi 上限、50-128Mi 請求）也是同一個 defaulting webhook 一起補的。

那個 w.cfg.AutoInstrumentationPythonImage 又是哪來的：versions.txt （autoinstrumentation-python=0.63b1）→ Makefile 用 awk 讀出來 → 編 operator 二進位檔時用 -ldflags -X 燒進 internal/version → internal/config.New() 拼成完整 image 字串，變成這個 operator 版本的內建預設值。 同一個值也能被 operator chart 的 manager.autoInstrumentationImage.python（§2.2 chart values 表） 或 AUTO_INSTRUMENTATION_PYTHON_IMAGE 環境變數整組覆蓋——覆蓋的是「這個 operator 部署的預設值」， 不是個別 CR，所以會影響到所有沒自己填 image 的 Instrumentation CR。

這個 defaulting webhook 還順手在 CR 上留了一條線索——把套用當下的預設版本寫進 instrumentation.opentelemetry.io/default-auto-instrumentation-python-image 這個 annotation。 目的是讓 internal/instrumentation/upgrade 的升級流程日後能分辨：這個 image 是你自己刻意 pin 的， 還是當初 operator 隨手補的預設值（如果是後者，operator 升級時可以放心幫你一起往前推）——呼應 §2.3 spec.upgradeStrategy 那套逐 CR 安全閥的邏輯。

對照組——如果平台團隊決定自己 pin 版本，不讓它跟著 operator 走，就是同一份 CR 多兩行：

apiVersion: opentelemetry.io/v1alpha1 kind: Instrumentation metadata: name: lab-instrumentation namespace: otel-lab spec: exporter: endpoint: http://localhost:4318 env: - name: OTEL_EXPORTER_OTLP_PROTOCOL value: http/protobuf propagators: [tracecontext, baggage] sampler: type: parentbased_always_on java: image: ghcr.io/open-telemetry/opentelemetry-operator/autoinstrumentation-java:2.28.1 # ↑ 明寫＝跟現在 operator 內建的預設剛好一樣，但從今以後 operator 升級也不會再動它 env: - name: OTEL_INSTRUMENTATION_COMMON_DEFAULT_ENABLED value: "true" python: image: ghcr.io/open-telemetry/opentelemetry-operator/autoinstrumentation-python:0.60b0 # ↑ 刻意停在舊版：團隊還沒驗證過 operator 目前內建的 0.63b1，先鎖住 env: - name: OTEL_PYTHON_LOG_CORRELATION value: "true"

兩個語言示範兩種心態：java 那行寫的版本跟 operator 現在的內建預設一樣，純粹是「先鎖住，之後 operator 升級也不會被動跟走」； python 那行才是真正的「自己選版本」——刻意停在比內建預設舊的 0.60b0，因為還沒驗證過新版 agent 的行為。 兩種都是合法用法，差別只在你的動機是「防止被動升級」還是「主動選一個不同的版本」。

第一部：擴散 · 收尾

紅線與漸進語意

紅線

已手動插樁的服務絕不加 inject-<lang>：operator 的防重複檢查只認自己注入的東西，不知道 image 裡的手動 agent。Java 的後果最具體——operator 往既有 JAVA_TOOL_OPTIONS 後面 append，兩個 agent 同時掛。

紅線

「移除手動配置」＝移除 provider 初始化，不是移除 SDK。業務 code 裡的 OTel API 呼叫全留；provider 改成無參數、由 env 自動配置。API/SDK 分界正是 OTel 留給平台治理的縫。

保證

漸進的機制保證：append-if-not-set 意味著團隊自己的 OTEL_* env 不會被蓋。還沒改完 provider 的服務先掛 sidecar annotation，改完再補 inject-sdk——每一步都可以獨立 rollback。

第二部：治理 · 拓撲分析

現況的結構性問題，與目標拓撲

兩個結構性問題，都不是「設定沒調好」，是拓撲本身的。

現況資料流
app SDK→ 手掛 sidecar→ span-lb.open-telemetry.svc（跨 namespace）→ Tempo / metrics 後端

問題一：k8s 屬性只能手工拼。 k8sattributes processor 靠連線來源 pod IP 反查 metadata； 資料一經任何中繼轉手，來源 IP 就不是原始 Pod。所以每個服務的 values 裡都手工拼了一份 OTEL_RESOURCE_ATTRIBUTES + Downward API env——同一段邏輯複製 N 份，這就是「治理缺位」的具體長相。Operator 的解法：注入 sidecar 時自動備好組好的 OTEL_RESOURCE_ATTRIBUTES（含 owner reference 反查的 deployment/replicaset 名稱），sidecar config 一個 resourcedetection（env detector）收工——不打 k8s API、不用 RBAC。 pkg/sidecar/attributes.go

現況：每個服務自己手拼（values.yaml）

env: - name: OTEL_RESOURCE_ATTRIBUTES value: >- k8s.namespace.name=default, k8s.pod.name=$(POD_NAME), k8s.node.name=$(NODE_NAME), k8s.deployment.name=llm-guard-api # 這行是手打的，改個服務名要記得同步改 - name: POD_NAME valueFrom: { fieldRef: { fieldPath: metadata.name } } - name: NODE_NAME valueFrom: { fieldRef: { fieldPath: spec.nodeName } }

Operator：webhook 注入時自動算好

Environment: OTEL_RESOURCE_ATTRIBUTES_POD_NAME: # downward API (v1:metadata.name) OTEL_RESOURCE_ATTRIBUTES_POD_UID: (v1:metadata.uid) OTEL_RESOURCE_ATTRIBUTES_NODE_NAME: (v1:spec.nodeName) OTEL_RESOURCE_ATTRIBUTES: k8s.deployment.name=llm-guard-api, k8s.deployment.uid=3f2a1c9e-..., # ← webhook 當下查 K8s API 反查出來，寫死的字串 k8s.namespace.name=default, k8s.node.name=$(OTEL_RESOURCE_ATTRIBUTES_NODE_NAME), # ← 這幾個要等 Pod 排程完才知道 k8s.pod.name=$(OTEL_RESOURCE_ATTRIBUTES_POD_NAME), # 所以用 downward API 間接參照 k8s.pod.uid=$(OTEL_RESOURCE_ATTRIBUTES_POD_UID), k8s.replicaset.name=llm-guard-api-7d9f8c6b5, k8s.replicaset.uid=8b6e2d41-...

兩邊的差別：webhook 在 admission 那一刻就能查到 Pod 的 owner chain(Pod → ReplicaSet → Deployment)， 所以 k8s.deployment.name／k8s.replicaset.name 這幾個是當下反查、直接寫死成字串； 但 Pod 自己的名字、UID、排到哪個節點，要等 Pod 真的建立、排程完才會確定，所以這三個改用 downward API 用 $(...) 間接參照—— 這就是為什麼 Pod 上會多出三個 OTEL_RESOURCE_ATTRIBUTES_POD_NAME 這類輔助 env，不是隨手多加的。

Sidecar 這邊的 collector config 只需要一行就能把上面這串吃進去：

processors: resourcedetection/env: detectors: [env] # 讀 process 環境變數裡的 OTEL_RESOURCE_ATTRIBUTES，僅此而已 service: pipelines: traces: processors: [resourcedetection/env, batch]

env detector 的實作只有一行關鍵邏輯：讀 os.Getenv("OTEL_RESOURCE_ATTRIBUTES")， 解析成 key=value 逐一掛上 resource——沒有 k8s client、沒有 List/Watch，所以不需要 RBAC， 跟 k8sattributes processor 那種要打 K8s API、還要考慮來源 IP 是否失真的做法完全是兩條路。

要做的事誰負責你要不要在 CR 裡寫
產生 OTEL_RESOURCE_ATTRIBUTES + 3 個 downward API envoperator webhook，無條件自動不用寫——寫了反而蓋掉自動版本
把這串 env 讀進 pipeline、變成 resource 屬性你自己在 spec.config.processors要寫 resourcedetection/env: { detectors: [env] }，並接進 pipeline 的 processors 清單

但這裡要分清楚兩件事，平台要宣告的其實只有一半。 上面那串 OTEL_RESOURCE_ATTRIBUTES 是 operator 無條件自動加的——只要這份 CR 是 mode: sidecar，webhook 組出 sidecar container 時就會呼叫 getResourceAttributesEnv 把它跟三個 downward API env 一起塞進這個 sidecar container 自己的 env（不是 app 那個 container 的 env）。 平台完全不用在 CR 裡宣告這件事，也宣告不了——除非你自己在 spec.env 手動設了同名的 OTEL_RESOURCE_ATTRIBUTES，operator 才會讓步不覆蓋（hasResourceAttributeEnvVar 那個檢查， append-if-not-set 又出現一次）。

平台真正要寫進 CR 的，只有 resourcedetection/env 這個 processor——因為決策三，operator 不會替你的 spec.config 加任何 processor 或改 pipeline，這行不寫，env 變數就靜靜躺在那裡沒人讀。完整的 sidecar CR 長這樣：

apiVersion: opentelemetry.io/v1beta1 kind: OpenTelemetryCollector metadata: name: llm-guard-api-sidecar # annotation 裡指到的就是這個名字 namespace: llm-guard-api spec: mode: sidecar config: receivers: otlp: { protocols: { grpc: {}, http: {} } } processors: resourcedetection/env: { detectors: [env] } # ← 平台唯一要手寫的一行 batch: {} exporters: otlp: endpoint: span-lb.open-telemetry.svc.cluster.local:4317 tls: { insecure: true } service: pipelines: traces: receivers: [otlp] processors: [resourcedetection/env, batch] exporters: [otlp]

再提醒一個容易誤會的地方：這串 OTEL_RESOURCE_ATTRIBUTES 蓋的是sidecar 收到資料之後幫它蓋章， 不是 app 自己 SDK 送出去時就自帶——app 那個 container 的環境變數完全沒被動到。app 端要不要自己也有 resource 屬性， 是 instrumentation.opentelemetry.io/inject-python（機制四那條線）另外處理的事，兩條注入路徑各管各的 env。

那條路一樣不用宣告——internal/instrumentation/sdk.go 的 injectCommonSDKConfig 會自動組出 k8s.namespace.name、k8s.pod.name、k8s.node.name、 k8s.container.name、service.instance.id，並且一樣沿著 owner reference 往上查 ReplicaSet/Deployment（addParentResourceLabels），寫進 app container 自己的 OTEL_RESOURCE_ATTRIBUTES。差別只有一點：不需要另外寫任何 processor 去「消化」它—— OTel SDK 啟動時本來就會自己讀這個環境變數，這是 SDK 規範內建的行為，不是 operator 額外做的事。

sidecar CR 那條路Instrumentation CR 這條路
Env 變數本身自動自動
要不要多寫一個「消化」設定要——spec.config.processors 加 resourcedetection/env不用——SDK 標準行為，啟動時自己讀
CR 裡可選填的加值欄位（無，config 透傳）spec.resource.resourceAttributes（自訂額外屬性，優先權最低）、spec.resource.addK8sUIDAttributes（預設關，開了才多查 UID）

問題二：tail sampling 沒有正確的前置條件。 多副本 gateway 做 tail sampling，同一 trace 的所有 span 必須進同一副本。 span-lb 這個名字暗示有做 span 層級 LB——要驗證它的 routing key 是不是 traceID；如果只是 Service 層的 L4 均衡， tail sampling 的決策一直在看片段。下方機制七直接動手驗這件事。

目標拓撲
sidecar（k8s 屬性蓋章）→ agent DaemonSet（routing_key: traceID）→ gateway StatefulSet × N（tail_sampling）→ 後端

agent CR（mode: daemonset）

exporters: load_balancing: routing_key: traceID resolver: dns: hostname: gateway-collector-headless... port: "4317"

gateway CR（mode: statefulset）

processors: tail_sampling: decision_wait: 10s policies: - { name: errors, type: status_code, ... } - { name: slow, type: latency, ... } - { name: rest, type: probabilistic, ... }

Gateway 用 statefulset mode 不是偏好，是 loadbalancing resolver 需要 headless service 的穩定 DNS—— 機制二的實驗已經示範過這件事。Sampling 政策只存在 gateway CR 一個地方；換後端不動任何業務部署。

Sidecar 的成本要誠實：per-pod 線性增長。買到 per-pod 身分蓋章、per-service 客製隔離、短生命週期 process 的就近 flush。三個都用不上的服務，讓 SDK 直送 agent 層即可，模型允許混用。

坑一

坑三

雙主人。發現 operator 管的資源「一直被改回去」，正確反應是去改 CR，不是加大力度改 Deployment。

存量遷移路徑

  1. 中央層不動。Operator 只管 sidecar + Instrumentation，sidecar exporter 照指 span-lb.open-telemetry.svc。中央層零變更。
  2. 中央 collector 的 config 從 chart values 搬進 CR。Service 名稱會變（operator 產生 <CR名>-collector）——切換期留一個舊名 ExternalName 當 alias，或反過來把切流量做在 sidecar CR 的 exporter endpoint。
  3. 新舊並行驗證後下掉 Helm 版 collector。隨時可切回：endpoint 改回去就好。

第二部：治理 · 版本治理

versions.txt 模型 vs 自建 image

Operator 的版本治理模型：versions.txt 把 collector、各語言 agent、target allocator 的版本釘成一組—— 發佈一個 operator 版本＝發佈一整組驗證過的元件版本。Operator 升級時，upgrade routine 主動把 cluster 裡所有 CR 遷到新 schema/預設值； spec.upgradeStrategy: none 和 spec.managementState: unmanaged 是逐 CR 的安全閥。

跟自建 image 直接衝突的現實：spec.image 明確指定時，operator 的自動版本升級不會動它——保留了自建 pipeline 的控制權， 但也放棄了「升 operator＝升全部 collector」的治理紅利。Collector 版本的治理責任仍在自己的 image pipeline。

建議做法：agent 交給 operator 治理（不 pin），collector 維持自建——兩者的客製需求不同（collector 有公司內部 exporter/processor 的需求，agent 沒有）。 自建 image 的升級節奏要跟 operator 版本對表（operator 解析 config 推導 port/RBAC，跨大版本的 config schema 變更兩邊要同步驗）。

平台治理團隊要盯版本，不用一個一個查 versions.txt 對照 changelog——官方所有元件的 image 都發佈在同一個地方：github.com/orgs/open-telemetry/packages（filter 成 opentelemetry-operator repo）。上面看得到 opentelemetry-operator、 target-allocator、operator-opamp-bridge 本體，跟 autoinstrumentation-java／ -python／-nodejs／-dotnet／-apache-httpd 這幾個 CR 裡會填的 image， 每個 tag 都能反查是哪次 release 帶出來的——決定「哪些交給 operator 自動升、哪些自己 pin 死」之前，先看這裡有沒有新版本。

裡面還有一個 autoinstrumentation-php——但它不代表 PHP 有自動注入。 這個 image 是 autoinstrumentation/php/ 目錄建出來的 PECL extension 檔案，純粹提供給要自己組 base image 的團隊拉取； InstrumentationSpec 沒有對應的 php 欄位、也沒有 inject-php annotation—— webhook 不會替你把它裝進任何 Pod。跟存量矩陣那節講的一樣：PHP 只能走 inject-sdk，這個 image 只是「原料」，裝進 image 是自己的事。

客製化語意Config 整份取代，無欄位優先權Env 逐項合併（append-if-not-set）
「這個服務想不一樣」只能 clone 一份 CR多數情況不用 clone——值留在 app 自己的 env 就贏了
拆分判準需求會分岔的團隊，現在就拆只有「endpoint/sampler/image/resources 這種 CR 層欄位」要不一樣時才拆

image／resources 屬於「CR 層欄位」，沒有 Pod 端覆蓋的逃生門。 查過 internal/instrumentation/annotation.go 全部的 annotation，Pod 能動的只有 inject-<lang>、 container-names，加上 python/dotnet/go 各自一個輔助 annotation——沒有任何一個能在 Pod 層級覆蓋 agent image。 跟 env 不同（四層合併，container 自己的值天生贏），image 就是整份 CR 共用一個值，誰引用就套誰。 某個服務想先試新版 agent、其他服務不動，唯一做法是 clone 一份 CR 讓那個服務的 annotation 改指過去。

不同語言要用不同版本，倒是同一份 CR 內建就會的事——每個語言各自一個獨立的 image 欄位，互不影響：

apiVersion: opentelemetry.io/v1alpha1 kind: Instrumentation metadata: name: company-default namespace: opentelemetry spec: exporter: endpoint: http://gateway-collector.open-telemetry.svc:4318 sampler: type: parentbased_traceidratio argument: "0.25" java: image: ghcr.io/open-telemetry/opentelemetry-operator/autoinstrumentation-java:2.28.1 python: image: ghcr.io/open-telemetry/opentelemetry-operator/autoinstrumentation-python:0.63b1 nodejs: image: ghcr.io/open-telemetry/opentelemetry-operator/autoinstrumentation-nodejs:0.203.0

Pod 端的 instrumentation.opentelemetry.io/inject-python annotation 指到這份 CR 時，operator 只挑 spec.python 那一段來用；同一份 CR 被 inject-java 的 Pod 引用時，只挑 spec.java—— 彼此互不干擾，不用因為語言不同就拆成多份 CR。

Sidecar CR 可以共用嗎？可以，機制上兩個常見疑慮都不成立：annotation 支援跨 namespace 引用； config 整份 inline 進 OTEL_CONFIG env，不落地任何 ConfigMap；per-pod metadata 是注入當下逐 Pod 計算的，不是從 CR 來的。 一份共用 CR，N 個 Pod 各自拿到正確身分。

共用的真正約束是三條：

  1. Config 必須 namespace 中立——exporter endpoint 用 FQDN。
  2. 避開 spec.configMaps/spec.volumes/secretKeyRef——這些以 LocalObjectReference 在 Pod 的 namespace 解析。
  3. Config 無合併語意——per-service 差異只能 clone。

Webhook 用 operator 的權限讀 CR，沒有「誰有資格引用哪份 CR」的授權檢查——per-team CR 防不了被別的團隊誤指，防線是 annotation 的 code review。

兩種 processor 各一段
processors: attributes/order_team: # 固定標籤：attributes processor 就夠 actions: - { key: team, value: "order-team", action: insert } - { key: cost_center, value: "CC-4821", action: insert } transform/order_team: # 條件 + regex 遮罩：才需要 OTTL trace_statements: - context: span statements: - replace_pattern(attributes["db.statement"], "(?i)VALUES\\s*\\([^)]*\\)", "VALUES (***redacted***)") where attributes["db.statement"] != nil

選型法則：固定 key/value 用 attributes；條件、regex、跨欄位才上 transform（OTTL）；合規更嚴用 delete_key。

一條實測教訓：Hibernate 產小寫 values，沒加上面那個 (?i) 的遮罩規則靜默不匹配——語法全對、collector 不報錯、資料照漏。OTTL 政策上線前要拿真實流量驗證命中率。

第二部：治理 · 兩條延伸路

TargetAllocator 與 OpAMP

TargetAllocator——現有 ServiceMonitor 資產有現成的收編路。若未來 metrics 也要進 OTel 管線， TA 的 prometheusCR.enabled 直接認得現有 ServiceMonitor/PodMonitor，各團隊已寫好的 monitor 一個都不用改。

OpAMP——多環境的控制面選項。每個 cluster 跑一個 bridge，把該 cluster 裡 operator 管的所有 collector 代理給遠端控制面： 回報 effective config、接受下推（回寫 CR，滾動更新交回 operator）、componentsAllowed 當白名單安全閥。

它跟 GitOps 是競合關係——同一份 CR 不能同時被 ArgoCD 和 OpAMP server 當 source of truth，選了 OpAMP 下推的欄位就要從 Git 管理範圍拿掉，否則兩個控制面互相打架。多環境如果 GitOps 已經順，OpAMP 的增量價值在「秒級動態調參」而不是常規變更。

收尾 · 落地路徑

對應現況的五個階段

  1. Helm 裝 operator；中央 collector 不動。對業務團隊的成本：零。
  2. 平台建兩份 Instrumentation CR（直送版/sidecar 版）+ 標準 sidecar CR；新服務與無 OTel 服務接入。對業務團隊的成本：兩三行 annotation。
  3. 手動裝過 OTel 的服務逐一遷移（llm-guard-api 模式：留 API、去 provider；拆 base image 旗標）。一次性遷移，每步可回退。
  4. 中央 collector 搬進 CR，agent+gateway 拓撲補上 traceID routing，灰度切換。對業務團隊的成本：零。
  5. 視需求：TA 收編 metrics、OpAMP 上多環境控制面、業務客製走專屬 sidecar CR。各團隊自理。

遷移論證的核心：遷移前，observability 設定散落在 app 的 Helm values，改政策＝改 app 部署；遷移後收斂到 CR， app 部署與 observability 政策解耦——同時每個服務刪掉一份手工複製的 k8s 屬性拼裝邏輯。

帶走的三句話

如果只記得三件事

  1. 擴散靠把介面壓窄：平台擁有政策（CR），業務團隊只表達意圖（annotation）；env 合併語意讓例外留在 app 端，不腐蝕共用範本。
  2. 治理靠迴圈，不靠自律：Helm 管交付、operator 管執行期；但兩種執行點的政策生效語意不同，收斂要量測。
  3. 知道機制的邊界：注入 best-effort、惰性生效、CRD 生命週期、自建 image 讓出的治理紅利——這些寫進 runbook 與架構決策記錄，而不是被它們 surprise。
